# Коммит и git-flow в expense-tracker

## Перед коммитом

Прогнать чек-лист:

```bash
pnpm lint && pnpm typecheck && pnpm test
```

Если менялся `apps/api` — ещё и:

```bash
pnpm db:up && cd apps/api && pnpm test:e2e
```

## Формат сообщения коммита

Conventional Commits, заголовок на русском в повелительном наклонении
(«добавить», «починить», а не «добавил» / «добавляет»), без точки в конце,
до 72 символов:

```
<тип>(<область>): <что сделано>

<почему так, а не иначе — если это не очевидно из диффа>
```

**Типы**: `feat` (новая функциональность), `fix` (исправление поведения),
`refactor` (поведение не меняется), `test`, `docs`, `chore` (сборка,
конфигурация, зависимости), `perf`.

**Область** — пакет, которого касается изменение: `api`, `web`, `shared`,
`config` (общие конфиги ESLint/TypeScript), `claude` (файлы `.claude/`).
Для изменений по всему монорепо область опускается.

**Тело сообщения** — не пересказ диффа, а причины: почему выбран этот подход,
какие альтернативы отпали и почему, какие границы задачи проведены сознательно.
Список изменённых файлов в тело не выписывать — он и так есть в самом коммите.

**Гранулярность**: один коммит — одна законченная единица работы, которая
собирается и проходит тесты сама по себе. Правки в чужом модуле, понадобившиеся
ради текущей фичи (например, новый запрос в `categories` ради `transactions`),
едут вместе с ней, а не отдельным коммитом «на будущее».

## Git-флоу (GitHub Flow)

Основная ветка — `main`, всегда в деплоящемся состоянии. Прямые коммиты в
`main` не делаются — вся работа идёт через короткоживущие фича-ветки и Pull
Request.

**Именование веток** — `<тип>/<краткое-описание-через-дефисы>` на английском,
тип — один из тех, что используются в Conventional Commits (`feature`, `fix`,
`refactor`, `chore`, `docs`), например: `feature/main-screen`,
`fix/transactions-summary`.

**Процесс**:

1. Новая ветка создаётся от актуального `main`:
   ```bash
   git checkout main && git pull && git checkout -b feature/...
   ```
2. Работа и коммиты — по правилам выше.
3. Ветка пушится в origin, открывается Pull Request в `main` через
   `gh pr create`.
4. Перед открытием PR — тот же чек-лист, что и перед коммитом
   (`pnpm lint && pnpm typecheck && pnpm test`, при правках в `apps/api` —
   ещё `pnpm test:e2e`).
5. Слияние — только через PR (Squash and merge или обычный merge, без
   `git push --force` в `main`), ветка после слияния удаляется.
