# Добавление теста на файл

Команда вызывается вручную:

```
/test <путь-до-файла>
```

`$1` — путь до файла, на который нужно написать тест (относительный от корня
репозитория или абсолютный). Если аргумент не передан — спросить пользователя,
какой файл покрывать тестом, не гадать.

## 1. Проверки перед началом

- Файл `$1` существует — если нет, сообщить и остановиться.
- Файл принадлежит одному из пакетов с тестами (`apps/api`, `apps/web`,
  `packages/shared`) — код в `react-leveling-plan/` и `dotnet-core-plan/`
  тестами не покрывается (см. корневой `CLAUDE.md`).
- Файл — не сам тест (`*.spec.ts`, `*.test.ts`, `*.test.tsx`) и не барабанный
  экспорт (`index.ts`, реэкспортирующий чужой код без своей логики) — для таких
  файлов тест обычно не нужен; если пользователь всё равно просит, уточнить, что
  именно проверять.

Определить, тест на файл уже существует рядом или нет:

```bash
ls "$(dirname <файл>)" | grep -E "$(basename <файл> | sed -E 's/\.(ts|tsx)$//').*(test|spec)"
```

Если файл теста уже есть — читать его и **дополнять** новыми `it`/`describe`
по тому же стилю, а не создавать второй файл рядом и не переписывать
существующие тесты без необходимости.

## 2. Определить конвенцию по расположению и пакету

Пакет диктует расширение и стиль (различаются оба пакета, где есть тесты):

| Пакет | Расширение | Раннер/либы | Пример |
|---|---|---|---|
| `apps/api` | `*.spec.ts`, рядом с исходником | vitest, без React; сервисы/хендлеры мокаются вручную через `vi.fn()`, без обращения к реальной Prisma/БД | `apps/api/src/categories/categories.service.spec.ts` |
| `apps/web` | `*.test.ts` (логика) / `*.test.tsx` (компоненты), рядом с исходником | vitest + `@testing-library/react` + `msw` (`@/test/mocks/server`) для мокания HTTP, `userEvent` для взаимодействий | `apps/web/src/features/categories/create-category/ui/create-category-form.test.tsx` |
| `packages/shared` | `*.spec.ts` или `*.test.ts` рядом со схемой | vitest, чистые функции/Zod-схемы, без моков | искать существующий аналог рядом |

Не выдумывать структуру с нуля — **прочитать 1–2 существующих теста того же
рода** (сервис/хендлер/контроллер в api; форма/диалог/виджет в web) рядом с
целевым файлом или в соседнем домене (например, для нового сервиса в
`transactions` — посмотреть на `categories.service.spec.ts`, для новой формы —
на `create-category-form.test.tsx`) и повторить их конвенции:

- именование `describe`/`it` — на русском, в изъявительном наклонении
  (`'бросает NotFoundException, если ...'`, `'рендерит поля формы ...'`);
- в `apps/api` — паттерн мока репозитория/зависимостей через объект
  `ReturnType<typeof vi.fn()>` и хелперы `buildX(overrides = {})` для тестовых
  сущностей;
- в `apps/web` — паттерн `renderForm()`/`renderComponent()`-хелпера, оборачивающего
  в `QueryClientProvider` с `retry: false`, и переопределение MSW-хендлера через
  `server.use(http....)` для проверки ошибок сервера.

## 3. Что покрывать

Прочитать целевой файл целиком и определить его публичное поведение:

- для сервиса/хендлера (api) — каждый метод: успешный путь, граничные случаи
  (не найдено → `NotFoundException`, конфликт уникальности → `ConflictException`
  и т.п.), проверка вызовов зависимостей с ожидаемыми аргументами;
- для формы/компонента (web) — рендер по умолчанию, валидация (клиентская —
  через Zod-схему формы, серверная — через ответ с ошибкой), успешный сценарий
  с колбэком (`onSuccess` и т.п.);
- для чистой функции/схемы (shared, `lib`) — корректные и некорректные входные
  данные, граничные значения.

Не тестировать приватные детали реализации и не мокать больше, чем нужно —
только прямые зависимости целевого модуля.

## 4. Написание теста

Создать (или дополнить) файл теста рядом с исходником, с расширением по
таблице выше. Следовать стилю найденного образца: импорты, оформление
хелперов, форматирование (кодовая база — Prettier, не подгонять руками).

## 5. Прогон

```bash
cd <пакет> && pnpm exec vitest run <путь-до-теста>
```

Для `apps/web` — `<путь-до-теста>` указывается от `apps/web` (например,
`src/features/.../create-category-form.test.tsx`). Тест не проходит — чинить
тест или (если найден баг в исходнике) сообщить пользователю о найденной
проблеме, не подгонять тест под неверное поведение.

После прохождения — прогнать lint и typecheck по пакету:

```bash
pnpm --filter <пакет> lint && pnpm --filter <пакет> typecheck
```
